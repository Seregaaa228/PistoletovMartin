# Самолёты: прицел, полёт, уничтожение и расширение

Запрос пользователя: ракеты должны попадать туда, куда прицеливается пушка;
самолёт после уничтожения взрывается и полностью исчезает; отзывчивое управление
нужно немного откалибровать, убрав ощущение бокового дрейфа. Новым моделям нужны
собственные настройки полёта и вооружение. Архитектура должна позволять позднее
писать ботов для воздушного боя через тот же контур, что используется игроком.

Основа остаётся Minecraft 1.20.1 / Forge 47.4.0 / Java 17. Сохраняются закреплённые
зависимости, native ID, форматы сохранений, промышленный ledger и preserved-combat.
Текущая схема ракетного спуска сохраняется: короткий клик — одна; удержание около
300 мс — две одновременно. Изменение не является разработкой поведения ботов.

## Принятые технические решения

Эти решения принимает исполнитель в рамках порученной реализации.

1. Каталог моделей связывает стабильный entity ID, FlightProfile, HandlingProfile,
   WeaponLoadout, правила уничтожения и необязательные сведения новой модели.
   Собственные сущности/предметы/рендереры создаются по каталогу. Native-модели
   получают описание управления без повторной регистрации сущности.
2. Model metadata не импортирует клиентские классы. Геометрия, native engine,
   magazines, heat, reload, explosion damage и runtime projectile остаются у SBW/DSM.
   Не создаются параллельный боезапас, второй интегратор движения или свои копии
   native-сохранений.
3. Прицел — точка в мире и проверенное направление, а не фиксированная поправка
   угла модели. Расчёт учитывает origin HUD, реальную точку подвеса, препятствия,
   начальную скорость носителя и native-наведение. Запрос клиента не считается
   доказательством видимости; сервер проверяет геометрию без загрузки чанков.
   Общая инфраструктура прицеливания не ограничивается наземными целями.
4. Полёт сохраняет инерцию. Поперечное демпфирование зависит от аэродинамического
   профиля и скорости; оно не телепортирует вектор скорости вдоль носа, не создаёт
   кинетическую энергию, не отменяет падение и не меняет вертолёты. Силы применяются
   в native-шаге, не при replay неподтверждённых команд.
5. Уничтожение имеет один терминальный переход. Используется штатный взрыв и
   его правила для пассажиров; затем сущность удаляется сервером и исчезает у
   наблюдателей. Повторные callbacks/загрузка старого wreck не создают новый
   взрыв или снова живую машину. Промежуточный wreck не остаётся столкновением.
6. AircraftController принимает LivingEntity и ControlLease на серверном потоке.
   Игрок и NPC используют FlightControlService: один пилот, epoch, возрастающая
   sequence, heartbeat, таймаут и нейтрализация. Бот не пишет yaw/power/ammo напрямую.
   API вооружения использует стабильный slot ID и native named gun, а не индекс
   оружия в HUD. Выбор оружия, готовность, предел залпа и серверное прицеливание
   проходят общий путь. Точный факт выстрела подтверждается native-состоянием
   после отложенной очереди; результат QUEUED не объявляется попаданием.
7. Упреждение движущейся цели — отдельная ограниченная математическая задача.
   Constant-velocity solver учитывает наследуемую скорость и время жизни.
   Он не выдаётся за решение траектории ракеты с ускорением или снаряда с gravity.

## Критерии проверки

Прицел: воспроизводимый наземный ориентир, пушка и ракеты в одну область;
несколько дальностей, положительный/отрицательный pitch, крен, обе подвески,
одиночный и парный спуск, движение носителя, помеха перед целью, пустой боезапас.
Нужны реальные native projectiles, а не только проверка mixin-дескрипторов.

Полёт: прогретый двигатель, разгон, прямой полёт, крен и разворот, отпускание
управления, малые скорости и падение; сверить направления скорости/носа и
отсутствие мгновенного изменения скорости. Чистые проверки фиксируют сохранение
продольного движения, уменьшение поперечной энергии и поведение границ.

Уничтожение: реальные lethal damage и столкновение, один взрыв, отсутствие
живой/сохранённой сущности и клиентского wreck после обработки; отдельно старый
wreck, reload/restart, dedicated server и наблюдающий второй клиент.

Расширение: новая тестовая definition получает отдельный handling/loadout без
добавления условных ветвей в сервис управления. Проверяется связь slot/native gun
с JSON и действующими ID. NPC в свежем мире приобретает реальную lease,
подаёт команды и использует native оружие; смена места/смерть/устаревшая epoch
должны прекратить его управление. Это не демонстрация готового dogfight AI.

Обязательны все проверки README, standalone contracts, Python unittest,
integration assets, offline Industry build и полная сборка, git diff --check.
Сценарии засчитываются только для реально проверенного SHA256. Непроверенные
условия остаются открытыми в отчёте; сборка не заменяет игровую приёмку.
