# Пакет для независимого ревью авиации

Этот документ можно передать другой проверяющей стороне вместе с исходниками из архива
`build/review/aviation-review-2026-10-26.zip`. Архив — снимок на время упаковки:
после любых изменений его следует пересобрать и сверить MANIFEST/хэши. Не считайте
его автоматически равным текущему рабочему дереву.

## Что проверять

Задача: плавное, предсказуемое управление 12 типами авиации Minecraft 1.20.1 /
Forge 47.4.0 / Java 17, запуск/остановка двигателя, тормоза, шасси/зависание,
серверные полномочия, клиентский прогноз и API для будущих ботов.
После первой установки пользователь сообщил о пропадании отклика мыши и A/D с
последующим резким поворотом в одиночном мире. Текущий код содержит исправления
replay/ACK/интерполяции углов/native clamp; их корректность тоже нужно проверить.

Исходный пакет ревью был создан для рабочего дерева ветки `codex/flight-controls`.
Поскольку файлы могут меняться после упаковки, перед ревью проверьте `review/MANIFEST.json`
и `review/SOURCE-LIST.txt`, затем убедитесь, что patch содержит tracked и untracked
файлы и соответствует исходникам архива. Обычный `git diff` не показывает новые
untracked-файлы; при проверке живого дерева используйте также `git status` и явно
включайте untracked source. Не делайте выводов о текущем JAR только по старому архиву.

## Порядок чтения

1. `AGENTS.md`, `README.md`, `BUILD-RU.md`, `CONTRIBUTING.md`: правила проекта,
   закреплённые зависимости и ограничения сохранений/preserved-combat.
2. `docs/aviation/FLIGHT-CONTROLS-RU.md`: игровое поведение и границы задачи.
3. `docs/aviation/CONTROL-CONTRACT.md`: нормативный контракт revision 4; изменения,
   сделанные после снимка пакета, должны отдельно перечисляться и сверяться с кодом.
4. `docs/testing/AVIATION-STEERING-STABILITY-2026-10-26.md`: исправления,
   воспроизведения, фактические проверки и текущий SHA256 JAR.
5. `docs/testing/AVIATION-CONTROLS-2026-10-26.md`: исторический первый проход
   для предыдущего JAR; его числа и протокол не подменяют текущую проверку.
6. Исходники и тесты, затем `review/evidence/`: журналы и прежнее независимое
   ревью как дополнительная информация, а не доказательство отсутствия ошибок.

## Приоритетные вопросы ревью

- Есть ли потеря/повтор ввода при задержке, нескольких пакетах за тик, паузе,
  смене фокуса/экрана, смене seat/epoch и синхронизации времени мира?
- ACK действительно означает обработанную моделью команду? Раннее получение,
  timeout, release, superseded input и новые mode requests обрабатываются согласованно?
- Сохраняются ли пределы углов и угловые скорости при replay, упоре и реверсе?
  Может ли readback восстановить скрытый угол за native пределом?
- Нет ли скачка при ±180°, дополнительной native коррекции или двойного шага
  модели/движения? Проверить как пилота, так и наблюдателя.
- Правильно ли учтено наследование Tom6 → Aircraft → Helicopter, отдельные
  коэффициенты/расход/звук/пределы, Su24 late throttle и native emergency/hover?
- Сессии/seat0/NPC API, запоздавшие команды и terminal BUSY не обходят права?
  Native autopilot, пассажирское оружие и UAV остаются работоспособными?
- Сохранения legacy/v1/повреждённые/будущие версии не теряют старые данные?
- Согласованы ли диапазон и обработка mouse sensitivity с реальным источником
  настройки? Проверить NaN/необычные значения чистого helper отдельно от vanilla GUI.
- Есть ли необоснованные предположения в тестах, неточные заявления в отчётах,
  незамеченные затраты CPU/памяти/трафика или пробелы проверки? Не считать число
  assertions метрикой качества управления или производительности.

## Запуск проверок

Для зафиксированного архива без полного окружения проекта достаточно JDK 17 и Python 3:

```sh
python3 review/run-pure-checks.py
```

Скрипт проверяет хэши пакета, компилирует чистые Java-классы во временный каталог
и запускает семь наборов проверок модели/ввода/сети/прогноза. Minecraft, Forge,
сторонние JAR и мир для этого не нужны.

В полном проекте, с уже заполненным закреплённым кешем:

```sh
GRADLE_USER_HOME="$PWD/vendor/gradle-cache" python3 tools/build.py --offline :aviation:check
```

Полный обязательный маршрут приведён в README. Native bytecode contracts требуют
точных зависимостей и подготовленного Forge cache; они не входят в чистый runner.
Архив не содержит сторонние JAR, production-бинарную сборку, кэши, миры, личный
профиль, учётные данные или адреса серверов. Запуск runner проверяет чистые наборы
по снимку архива, но не актуальное рабочее дерево и не native bytecode hooks.
Для полного Gradle/native ревью нужен исходный проект с закреплёнными локальными
зависимостями; для вывода о поведении — отдельная игровая приёмка.

## Контракт результата ревью

Отчёт должен начинаться с таблицы `P0/P1/P2/P3` и для каждого замечания указывать
файл и строку или раздел, точный триггер, последствие, доказательство и минимальную
проверку. Разделяйте `доказано кодом`, `подтверждено чистым тестом`, `подтверждено
структурной проверкой` и `требует игрового стенда`. Число assertions, успешная
компиляция и старый JAR сами по себе не являются доказательством удобства,
native-физики или multiplayer.

Если предлагается изменение физического коэффициента, сначала приложите baseline,
метрику и воспроизводимый сценарий A/B; без этого разрешены только исправления
контракта, валидации, тестов и документации. Любое изменение протокола, native ID,
NBT или порядка перехвата требует отдельного решения и совместимой миграции.

## Готовое задание другой нейросети

```text
Проведи независимое критическое code review приложенной реализации управления
авиацией Minecraft 1.20.1 / Forge 47.4.0 / Java 17. Начни с REVIEW-PACKET-RU.md,
затем изучи контракт revision 4 и фактический код, включая новые файлы из patch.
Проверь перечисленные риски и найди другие конкретные ошибки самостоятельно.
Не принимай прежние отчёты ревью или число тестов за доказательство корректности.

Сначала выдай найденные проблемы по серьёзности: файл/строка, конкретный триггер,
почему возникает ошибка, наблюдаемое последствие и минимальный способ проверки.
Отдели доказанные дефекты от гипотез, требующих игрового запуска. По возможности
приведи маленький регрессионный тест или числовое воспроизведение. Не ограничивайся
стилистическими замечаниями и не предлагай менять закреплённые зависимости.

Если подтверждённых ошибок нет, укажи это и перечисли реальные пробелы проверки.
Не утверждай, что поведение в игре или multiplayer проверены по компиляции.
Игровое поведение проверяет владелец; без отдельного поручения игру не запускай.
Не меняй production-код в ходе ревью: сначала предоставь результаты и предложения.
```
