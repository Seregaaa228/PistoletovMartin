# Проверка PIS-3/PIS-4

Основа: Java17, Minecraft1.20.1, Forge47.4.0, SmartBrainLib1.15,
GeckoLib4.8.4. Использовать отдельный свежий мир и профиль с integration manifest;
пользовательские миры и личный .minecraft не подходят. В отчёте записать runId,
SHA256 итогового Industry JAR/зависимостей, seed, view/simulation distance, CPU,
память JVM, сервер/клиент и частоту кадров. Успешная компиляция не заменяет этот
игровой прогон.

## Серверный контракт

Существующий frontier_industry:worker получает SmartBrain только для ролей
factory_repair и grid_repair. Назначение остаётся в IndustryData.Worker.site,
а прогресс, резерв одного комплекта и приказ — в прежних полях IndustryData.Site.
Sensor проверяет назначенную цель раз в 20–39 тиков; поиск пути запускается не
чаще раза в 100 тиков, один проход ограничен 200 тиками. Новые заказы sensor не
создаёт. Он проверяет текущие права страны у входа через ClaimPermissions.

Ремонт требует живого свободного рабочего в том же измерении, подхода к входу
на 2,5 блока и соответствующей роли. Проверка повторяется перед каждым шагом
общего заказа. Единственный IndustryEngine.repairCrew увеличивает сохранённый
прогресс один раз за серверный тик независимо от числа работников. 1800 рабочих
тиков = 90 секунд при 20TPS. Отсутствие энергии само по себе не запрещает ручной
или бригадный ремонт электросети.

Смерть/смена роли/занятость/отмена/исчезновение цели/выгрузка снимают готовность и
гасят рабочую анимацию. Смерть не возвращает сохранённого рекрута. После выгрузки
продолжение использует тот же UUID и журнал, без создания новой сущности.
Новый repair_cancel отличается от существующего cancel производственной
очереди: возвращает ровно один зарезервированный комплект и сбрасывает приказ.
При полных входных слотах отмена целиком отклоняется с объяснением.

Pure projection RepairWork.snapshot(server, site) добавляется в repairState:
requested, progressTicks, totalTicks, kitReserved, requiredRole,
workers (готовые у входа), assignedWorkers, reason, crew (id/state/reason).
Она не опрашивает/меняет блоки и не загружает чанки. Родительский snapshot сначала
проверяет доступ игрока. Состояния: idle/moving/repairing/no_path/no_materials/
unloaded/cancelled/target_missing/unauthorized/occupied/complete/dead.

## Автоматические проверки

    javac -d /tmp/frontier-repair-checks modules/industry/src/main/java/dev/frontier/industry/repair/RepairRules.java modules/industry/src/test/java/dev/frontier/industry/repair/RepairRulesTest.java
    java -cp /tmp/frontier-repair-checks dev.frontier.industry.repair.RepairRulesTest

12 standalone checks проверяют расстояние, чужого владельца, выгрузку, отмену,
завершённую цель, недоступного работника и ограничение повторного поиска пути.
RepairRuntimeChecks.run() содержит шесть native ItemStack/NBT проверок для
отдельного тестового раннера: атомарная отмена/повторная отмена/полный вход,
отсутствие бесплатного комплекта и восстановление назначения/прогресса1799.
Эти проверки требуют зарегистрированных Forge предметов и не запускаются
обычным standalone java. Ассеты имеют редактируемые исходники в
modules/industry/art/repair; JSON/PNG проверки не подтверждают вид в игре.

## Сценарии свежего мира

1. Создать страну, завод и отдельные станцию/подстанцию. Нанять заводского
   ремонтника и электромонтёра существующими кнопками. Проверить цену8 изумрудов,
   предел64 рабочих/7 армейских переводов и возврат снаряжения рекрута без копий.
2. Повредить по одному пустому блоку завода/подстанции, поставить один комплект
   во вход каждой цели. Заказать ремонт. Рабочий проходит к входу, отсчёт начинается
   после подхода. Заводской рабочий не назначается на сеть и наоборот.
3. Отодвинуть рабочего за 2,5 блока от входа: прогресс стоит. Перекрыть проход,
   показать no_path и пять секунд между попытками. Убрать препятствие: работа
   возобновляется. Недоступная цель не должна завершиться удалённо.
4. Назначить двух рабочих на один объект: один комплект, ровно1800 рабочих тиков,
   одно восстановление. Заполнить входы перед отменой: отказ без потери резерва;
   освободить слот: один возврат. Повторная отмена ничего не добавляет.
5. На прогрессе1799 сохранить/перезапустить сервер и отдельно выгрузить/загрузить
   чанк. UUID/назначение/резерв/прогресс сохраняются; следующий допустимый рабочий
   тик завершает операцию. Проверить смерть, увольнение, отмену и удаление цели
   по отдельности; отсутствие копий рабочих/рекрутов/комплектов.
6. На двух клиентах увидеть одинаковые idle/walk/repair и work/stop пресса.
   Потеря энергии/материалов/производственных рабочих и заполненный выход гасят
   пресс, сохраняя очередь. Восстановление энергии без реальной работы не запускает
   пресс. Переподключение восстанавливает актуальное состояние.
7. На dedicated server проверить отсутствие загрузки классов
   dev.frontier.industry.client.repair.*; на клиенте проверить текстуры, масштаб,
   оси каски/рук/поршня, отсутствие двойного статического пресса и дальнее отображение.

## Нагрузка20NPC и доказательства

Одинаковая сцена: один завод и одна повреждённая подстанция, по десять назначенных
ремонтников соответствующей роли; один комплект на объект. Контрольная сцена —
те же блоки и очереди с нулём ремонтников. Одинаковые JVM/seed/view distance,
отключённые прочие нагрузки. Прогреть1200тиков, записывать2400тиков; отдельно
повторить с перекрытыми входами. Между повторениями вернуть одинаковое повреждение.

Для серверного раннера собрать MinecraftServer.tickTimes[(tick-1)%100] один раз
за tick-END; первые1200тиков отбросить. Сохранить count/mean/p50/p95/max в миллисекундах,
число рабочих, число попыток пути и результат ремонта. Сравнить0/20 работников,
а не клиентский FPS с серверным MSPT. Для визуальной сцены записать короткое видео
ожидание→ходьба→ремонт, остановку пресса и скрин второго клиента. Пока такой прогон
не выполнен, не отмечать соответствующие Jira критерии выполненными.

## Test-only интегрированный раннер

Pis1WorldFixture в src/integrationTest регистрируется отдельным helper-модом.
Он дополнительно требует frontier.pis1Smoke, совпадающий runId в test-profile.json,
worldsCopied=false, локальный интегрированный сервер и готовый клиент. Для нового
прогона Industry ledger должен быть пустым; занятая площадка отклоняется до
замены блоков. Арена находится около4096/180/4096; состояние обычного профиля
не используется. В мире фиксируется полдень и выключаются естественные мобы,
смена времени и погоды; эти параметры записываются в JSON.

Обычный прогон включает30 GUI снимков на Scale2/3/Auto, реальную кнопку заказа,
разрушение подстанции, независимое повреждение завода,1800 рабочих тиков ремонта
двумя NPC, снимки world-repair/world-press и две фазы0/20NPC. Результат —
pis1-world-checks.json в отдельном тестовом профиле. Флаг
frontier.pis1SkipBenchmark=true сокращает отладочный прогон до UI/механики;
frontier.pis1BenchmarkOnly=true выполняет только одинаковую сцену0/20NPC и
использует общий API, существовавший в baseline. В каждой фазе1200тиков прогрева
и2400 замеров. Раннер запрашивает сохранение/выход через frontier.pis1Stop.
Отдельный повторный запуск с frontier.pis1Restart=true проверяет сохранённый
ledger без создания новых объектов и пишет pis1-world-restart-checks.json.
