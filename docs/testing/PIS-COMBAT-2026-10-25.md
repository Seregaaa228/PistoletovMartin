# PIS-9 / PIS-10 — multiplayer combat

Ветка: `codex/pis-9-10-multiplayer-combat`. Базовый commit:
`dc913b03c499798be606175f0326ec9d17498de3`.

Minecraft **1.20.1**, Forge **47.4.0**, Java **17** и закреплённые зависимости
сохранены. Рабочая папка до задачи уже содержала отдельные изменения Nations,
карты и КПК: они не отменялись и не приписываются combat-задаче. Коммита,
публикации и изменения статуса Jira этот отчёт не подразумевает.

Площадной взрыв native ракеты также сохраняет настоящего доступного владельца
по уже записанному UUID. Исправлено ошибочное сравнение отсутствующего стрелка
с отсутствующим historical driver (`null == null`), из-за которого пустая
техника отклоняла легитимный взрыв. Исправление ограничено explosion-уроном
с настоящим Guided source. Для offline/неизвестного UUID не создаётся
подставная сущность; настоящий self-driver и защита союзников сохраняются.
Исходный damage-type holder, direct source, координаты, радиус и расчёт брони
не заменяются. Штатная броня по-прежнему может полностью поглотить слабый
разрыв: это отдельно отличено от ошибки регистрации попадания.

## Настройки и ограничения работы за тик

В `serverconfig/frontier-aircraft-combat-server.toml`: `enabled`,
`blockDamageScale=0.4`, `maximumBlockHardness=5`, `blocksPerTick=16`.
При native direct damage 35 доски требуют один контакт, камень и кирпич —
два, железный блок — три; bedrock не повреждается. Partial damage хранится
до 100 тиков, не более 4096 позиций на измерение, без мирового сканирования.
Клинок в руке creative-пилота не меняет работу самолётной пушки.

В `serverconfig/frontier-missiles-server.toml` raw direct damage по типу:
FP5 **300**, Storm Shadow **220**, JAGM **150**, Peacekeeper **400**,
Spike NLOS **120**. Множители БЧ: none 0.30, HE/FP5 graphite 1,
penetrating 1.35, cluster 0.65, thermobaric 0.8, nuclear 2.5,
shaped_charge 1.75. Native допустимые сочетания БЧ сохраняются.
Это намеренная настройка direct component по PIS-15; значения native splash
не заменены. Реальная потеря здоровья зависит от native брони и модификаторов.

Движение FPV ограничено проверяемым сегментом 32 блока; неизвестный путь
не становится воздухом. Дополнительный поиск OBB использует только
загруженный entity index в радиусе 48 блоков и точную narrow phase:
расширенная коробка не является попаданием. Проверка authored геометрии
`python3 tools/check_combat_vehicle_bounds.py`: **429 OBB / 129 definitions**,
наибольший консервативный радиус **41.6653** (Kirov), меньше 48. Отдельное
вращение части учитывается суммой радиусов; runtime проверки используют
настоящие текущие OBB. Aircraft collision имеет общий бюджет 4096 voxel
кандидатов на все повторные sweep и ограниченный probe 32 блока.

Terrain mesh ракеты теперь строится отложенно: пустой/неизвестный voxel
не создаёт преобразованные кубы модели. На первом настоящем препятствии
строится ровно один прежний native mesh для этого сегмента. Поза и видимость
частей снимаются сразу, без округления углов, кеша мира или удержания entity.
В headless-проверке **28 577** assertions проверяют совпадение native геометрии,
контактов, snapshot видимости и однократное построение. Для 1000 одинаковых
воздушных сегментов JAGM измеренные allocations: **129 840 000 → 272 096 байт**
для snapshot, плюс приблизительно 24 байта marker на сегмент. Это измерение
конкретного участка кода, а не обещание такого же ускорения всего сервера.
В настоящем Forge отдельно проверены 300 native sweeps пяти типов:
100 воздушных и 100 через неизвестную землю не строят mesh/не грузят chunk;
100 контактов с камнем строят ровно один native mesh каждый.
В исходном late-stage JFR под `MissileShapeSweep.prepare` находились 84.1%
sampled allocation weights серверного потока; в итоговом профиле нет samples
этого участка ни в allocations, ни в CPU. Это подтверждает удаление данного
источника нагрузки, но не означает такое же изменение общего TPS:
остаются native управление чанками, сериализация и остальная симуляция.

## Воспроизводимый стенд

```sh
GRADLE_USER_HOME="$PWD/vendor/gradle-cache" python3 tools/build.py --offline build :industry:combatAcceptanceJar
python3 tools/verify_project.py
python3 tools/check_combat_vehicle_bounds.py
python3 tools/run_combat_checks.py --latency-ms 80 --profile
```

Linux runner использует точный `vendor/server-runtime`, Xvfb и два настоящих
Forge-клиента `CombatOwner` / `CombatGuest`. Создаёт новые `run-combat-*`
профили, новый flat-мир, loopback offline сервер с двумя игроками.
`--latency-ms 80` добавляет 80 мс в каждую сторону после входа, через
scheduled Netty callbacks; игровой/сетевой поток не усыпляется.
Опция `--profile` записывает JFR сервера в стадии дальних маршрутов и требует
Java 17 `jcmd`. JFR содержит локальные диагностические данные и не публикуется
в Git. При сравнении профилей учитывайте генерацию/выгрузку чанков и сохранение
мира: sampled allocations не являются точным счётчиком всех выделенных байт.

Helper — отдельный opt-in JAR
`modules/industry/build/acceptance/frontier-combat-checks.jar`. Нужны и JVM
флаг, и совпадающий marker/runId с `worldsCopied=false`. Он не входит в
production JAR или `build/team-mods`. Только тестовый пилот имеет creative
admin exemption к автоматически возникающим клеймам Living Villages;
отдельный отрицательный BreakEvent-тест проверяет запрет разрушения.
Teleport fixture настоящего игрока выдерживает 12 тиков перед выстрелом,
чтобы native hitbox history содержала уже видимую удалённому клиенту позицию.

JSON-результаты, timing, test-profile markers, логи, screenshots и короткая
запись экрана сохраняются в игнорируемом `vendor/combat-evidence` при уборке
старых созданных профилей. Пользовательские миры и личный `.minecraft`
не использовались. Два принятых `.class` Industry не заменялись исходниками.
