# PIS-13 / PIS-14 — серверные попадания FPV и Герани-2

## Причина и бинарные доказательства

Проверены `javap -c -p` именно закреплённые зависимости:

| Файл | SHA-256 |
|---|---|
| `uncomplicated-fpv-1.0.1.jar` | `289f5ac93d67aaf0e008c7080758569e2d09b91c0df44065b833d49ce39c35de` |
| `superbwarfare-0.8.9.1-hotfix-mc1.20.1-993063bed-all.jar` | `3aaf4c239bc0fb31f9217927a44d74071d904d1dd03c5308ca3395ecd67d86dc` |
| preserved `NativeCombatEvents.class` | `8bdda1168156fa9ce5577498fb0d7f1b42a29938ed2b4ef3851393f45b56f407` |
| preserved `ReadyWeapons.class` | `9460e139b74ff680895b2d40065fb18dc9a41e4105e2ded05ba2aec28a29eef9` |

`FpvDroneEntity` наследует `DroneEntity.destroy()` и его `kamikazeExplosion()`.
Последний возвращается без взрыва, если `CONTROLLER` не разрешается в живого
игрока. При потере сигнала `AddonDroneEntity.handleSignalLoss()` записывает
`CONTROLLER="none"`. Поэтому аварийный удар с заряженным боеприпасом после
потери связи теряет повреждение, хотя FPV корректно определяет свой боеприпас.

Вторая независимая проблема: `DroneEntity.travel()` проверяет сущности только
в небольшой коробке текущего положения. Между двумя положениями быстрого FPV
цель может вообще не оказаться в этой коробке. Старый прямой удар также мог
сочетаться с повторным `destroy()` и отдельным площадным повреждением.

Важная особенность SBW: `CustomExplosion.explode()` разрушает блоки через
`processBlockList()` до `ExplosionEvent.Detonate`, а последующие волны ставит
в очередь сервера. Фильтрация только `getAffectedBlocks()` на Forge-событии
не ограничивает фактическое разрушение. Новое ограничение стоит непосредственно
на аргументе `processBlockList()` и учитывает общий бюджет всех его волн.
В `explode$lambda$2` чтение незагруженного чанка заменяется непроходимым блоком.

Обе preserved `.class` только прочитаны. В `NativeCombatEvents` нет обработчика
взрывного friendly fire; его проверки `CombatOwnership` относятся к выбору
целей ПВО. Новая политика PvP/дипломатии не добавлена: повреждение продолжает
проходить native `DamageHandler` и Forge-события.

## Контракт исправления

Сохранены ID `uncomplicatedfpv:fpv_drone` и
`frontier_arcade_vehicles:geranium_2_drone`, регистрация, сеть и форматы NBT.
Для FPV требуется реально заряженный разрешённый native боеприпас и известный
владелец. Отсутствующий игрок больше не отменяет уже существующий боеприпас:
UUID остаётся в `frontierIndustryVehicleOwner`; источником атрибуции при offline
владельце остаётся сам принадлежащий ему FPV. Неизвестному владельцу бесплатный
взрыв не создаётся. Пустой FPV не получает боевую часть автоматически.

| Native боеприпас | Прямой урон | Площадной урон | Native радиус |
|---|---:|---:|---:|
| `superbwarfare:rpg_rocket_standard` | 340 | 80 | 5 |
| `superbwarfare:rpg_rocket_tbg` | 250 | 150 | 11 |
| `superbwarfare:mortar_shell` | 60 | 100 | 8 |

Значения читаются из закреплённой `CustomData.DRONE_ATTACHMENT`; таблица
фиксирует её текущие JSON. Прямой удар проходит один раз с native типом
боеприпаса. Его цель исключается из площадного списка этого же взрыва до
планирования повреждений. Другие цели получают native площадной урон.
Исключение выполняется с приоритетом **HIGHEST**: SBW
`LivingEventHandler.onExplosionDetonate()` на **NORMAL** самостоятельно
извлекает технику из списка и сразу вызывает её `hurt()`. Исключение на
LOWEST было слишком поздним для брони, хотя проверка коровы давала ровно 340.
Одноразовый серверный флаг предотвращает повторный `hitEntityCrash/destroy`.
Боеприпас расходуется до любых повторно входящих обработчиков.

FPV разрушает до **96** выбранных native взрывом блоков в радиусе **3 м**.
Герань сохраняет **300 урона / 16 м native радиуса**, разрушая до **256**
блоков в радиусе **6 м**. Это общий бюджет взрыва, включая отложенные волны.
Сохраняются native сопротивление/выбор блоков, drops и `onBlockExploded`;
сначала расходуются ближайшие допустимые блоки каждой native волны.
Неразрушаемые блоки не удаляются. При физическом разрушении Industry продолжает
определять повреждённые критические узлы своим существующим опросом; оплаченные
очереди и сохранённые сайты этим кодом не переписываются.

Сервер проверяет ближайшее пересечение за перемещение до **32 м/тик**.
Для SBW техники используются её реальные повёрнутые OBB, для остальных
сущностей AABB. Блок ограничивает дальность поиска: цель за преградой не
выбирается. Исходные монитор/пульт/связь остаются native. Незагруженный путь
или недопустимое перемещение останавливают вооружённый FPV/Герань без взрыва и
без генерации чанков. Нет сканирования всего мира и новых сетевых сообщений.

## Проверки

Выполнено на Java17:

```
GRADLE_USER_HOME="$PWD/vendor/gradle-cache" python3 tools/build.py --offline :arcade:compileJava :arcade:warheadRulesTest
```

Результат: `BUILD SUCCESSFUL`, `WarheadRulesTest: 25 checks passed`.
Это компиляция и чистые проверки правил, а не подтверждение загрузки mixin.
После этого добавлена остановка движения перед незагруженным путём; итоговая
сборка и runtime-проверка входят в общий запуск ответственного агента.

`modules/industry/src/combatAcceptance/.../DroneChecks.java` — отдельный
opt-in helper для свежего мира с двумя реальными клиентами. Он проверяет 80
попаданий native FPV через `move()` по коровам, LAV-150, T-90A и БМП-2 — по 20
каждого вида (10 неподвижных и 10 движущихся), потерю сигнала, повторный
`destroy()`, промах, пустой FPV,
неизвестного/offline владельца, реальное ограничение блоков и больший эффект
Герани. Он не входит в production Arcade. Итоговый runId, SHA выпускных JAR
и фактический результат выделенного сервера фиксируются в общем отчёте PIS-9/10.

Поведение реальных сетевых входов, движущейся цели между клиентскими кадрами,
native броневых множителей и сохранения/перезапуска нельзя доказать одной
компиляцией; это границы приведённого здесь локального результата.

## Дополнительный аудит native наземных снарядов и TaCZ

TaCZ `tacz-1.20.1-1.1.8-hotfix2.jar`, SHA-256
`2cbb89f44333d2eb4e825d86d789ff119b272ff75184390b55bafd4f0e7f10c2`,
проверен через `javap -c -p` без изменения стороннего JAR.

В SBW `FastThrowableProjectile.tick()` уже строит отрезок
`position → position + deltaMovement`, находит первый блок, ограничивает им
отрезок поиска сущностей и выбирает строго ближайшее пересечение. Один
результат передаётся в `onHit()` на native серверном тике. Владелец, его техника
и native запрет `Player.canHarmPlayer` исключаются. `IAdvancedHitDetection`
проверяет реальное пересечение повёрнутых OBB техники; для игроков использует
native историю hitbox/скорости с учётом ping стрелка. `SmallCannonShellEntity`
после столкновения вызывает native повреждение/взрыв и удаляется.

В TaCZ `EntityKineticBullet.onBulletTick()` также проверяет полный отрезок
движения, ограниченный первым блоком. `EntityUtil.findEntityOnPath()` выбирает
ближайшую живую сущность и использует `HitboxHelper.getFixedBoundingBox()`.
У пробивающих боеприпасов выбор нескольких целей и уменьшение `pierce` —
явная native механика; её нельзя заменять глобальным правилом «одна цель».
Обычный исчерпавший пробитие снаряд удаляется сразу после попадания.

Здесь подтверждена структура поиска и один выбранный native callback на
обычном тике. Это не доказательство всех исходов урона: прямой удар и splash,
TaCZ armor-piercing/non-armor-piercing и native броня являются отдельными
компонентами одного попадания. Отдельной защиты от искусственного многократного
ручного вызова каждого стороннего callback этот аудит не устанавливает.
Контрпримера native туннелирования в этих двух путях по байткоду не найдено;
новые production-перехваты для них не добавлены.

Дополнительный opt-in `GroundProjectileChecks` создаёт 20 native
`SmallCannonShellEntity` с фактическим движением **24 м/тик** через обычный
`ServerLevel.tick`. Native значения сохранены: **40 direct / 80 splash / 5 м**.
Снаряд начинает проверку после native muzzle grace. Пять случаев приходится
на каждый тип цели: БМП-2, T-90A, `recruits:recruit`, второй настоящий игрок;
в каждой группе есть движение и неподвижное положение. Sentinel позади цели
проверяет именно ближайший native `ProjectileHitEvent.HitEntity`; урон и
удаление снаряда фиксируются отдельно. Это проверка одного типа снаряда,
а не всех пушек, режимов огня, сетевых задержек или всего TaCZ.
Временное состояние тестового игрока восстанавливается после серии.

Helper самостоятельно сохраняет `combat-drone-results.json` и
`combat-ground-projectile-results.json`, чтобы сбой независимого этапа общего
runtime не скрывал уже собранные данные. Фактические результаты относятся
только к указанному runId и SHA общей тестовой сборки.

## Полученные runtime-данные до расширения серии

В отдельном выделенном сервере с двумя клиентами в профиле
`run-combat-2cdb0c7c-server` выполнена прежняя короткая FPV-серия:
**51/51 проверок**, 20 попаданий (по пять каждого типа цели), без ошибок.
В реальном тесте блоков FPV удалил **9**, Герань — **256** блоков.
Полный runId: `e58e0150-0020-4cbe-849c-83faf1563d7e`.
SHA-256 проверенного Arcade:
`60dc6a4b5adb6da2a84d3a0c048c94bc5f7767ca9d64511904cc25c83fb03dca`;
helper: `4c711663fef17db314b959effc33a9b6da743c5c0d464e579f2f01671094671c`.
Результат прочитан из `combat-drone-results.json`; это не означает успешность
независимых артиллерийских/промышленных этапов того же запуска.

Helper после этого расширен до **80 попаданий / 306 булевых проверок**:
по 20 попаданий каждого типа, 10 неподвижных и 10 движущихся, 16 потерь связи,
20 точных проверок 340 урона коровам и сохранённые проверки безопасности/блоков.
Для каждого из 60 попаданий по технике добавлены две независимые проверки:
приоритет HIGH подтверждает отсутствие прямой цели до native NORMAL-адаптера;
немедленное здоровье реальной цели сравнивается с отдельной native копией
того же типа/NBT, получившей только один native RPG-удар 340. Копия и источник
боеприпаса не добавляются в мир и не получают тика разрушения; броневые
множители и ограничение здоровья вычисляет установленный SBW. Класса
`VehicleHurtEvent` в закреплённом SBW нет, поэтому счётчик такого события
для доказательства не используется.
Эта расширенная серия требует нового запуска с новым SHA helper; предыдущие
51/51 её не заменяют и не доказывают отсутствие второго урона технике в старом
варианте обработчика LOWEST.

## Проверка внешних частей техники после независимого ревью

Первый поиск DroneSweep по vanilla AABB пропускал крылья, выступающие за
стандартную коробку самолёта. Кандидаты OBB теперь запрашиваются из
загруженного entity index в консервативном радиусе 48 блоков, затем
проверяются точными native OBB. Обычные сущности сохраняют узкий коридор
0.25 блока. Новых загрузок чанков нет. Все 388 authored OBB закреплённых
SBW/DSM JSON проверены: максимальный поворотно-инвариантный радиус
`norm(abs(Position)+Size)` равен 41.6653 блока (Kirov), меньше 48.
Игровые проверки внешнего крыла и итоговые результаты — в общем отчёте.
