# PIS-1: выделенный сервер и два клиента

Статус: свежий V9 прошёл 63/63 проверки и 13 этапов с подтверждением обоих
реальных клиентов; отдельный операторский сценарий книги → Mavic прошёл 26/26.
Владелец явно разрешил принятие EULA для отдельного тестового сервера проекта.
Тестовый helper не принимает EULA самостоятельно; launcher требует уже
принятый eula.txt.

## Подготовка

Нужны три разные рабочие папки, созданные tools/create_test_profile.py с
интеграциями: одна серверная и две клиентские. Во всех — test-only helper JAR
из integrationTestJar и совпадающие итоговые Industry/зависимости. Профили
worldsCopied=false; каждый launcher проверяет собственный runId. Используется
Java17/Minecraft1.20.1/Forge47.4.0, чужие миры не копируются.

Серверный профиль должен иметь уже установленный точный Forge server runtime.
Перед разрешённым запуском настроить server.properties для изолированного
локального теста: server-ip — буквальный IPv4/IPv6 loopback, online-mode=false
для предусмотренных launcher-ом локальных offline профилей; port выбрать
свободный. Пустой bind или hostname helper отклоняет. Не включать RCON/query и
не открывать порт наружу. Эти настройки относятся только к данному тесту.

Дополнительные JVM свойства сервера:

    -Dfrontier.pis1DedicatedAcceptance=true
    -Dfrontier.pis1OwnerName=Pis1Owner
    -Dfrontier.pis1ForeignName=Pis1Foreign

Обязательные smoke/runId свойства уже выставляет run_test_server.py. Новый
dedicatedAcceptance флаг ещё требуется передать launcher-ом явно; по умолчанию
сценарий выключен. При выключенном флаге обычные native suites не меняются.

После разрешённого запуска сервера два клиента запускаются существующим
tools/run_test_client.py с разными профилями, параметрами --server/--port и
разными --username Pis1Owner/Pis1Foreign. Helper подключает каждое окно через
ConnectScreen из guarded title-screen ветки, без ручного выбора сервера и без
записи адреса в servers.dat. Два отдельных Java процесса/окна нужны; вручную
соединять их с сервером не требуется. Это два реально подключённых ServerPlayer,
не FakePlayer и не два представления одного UUID.

## Серверная проверка

Pis1DedicatedFixture включается только для DedicatedServer. Дополнительно
проверяются matching fresh manifest, размещение мира внутри профиля, уже
принятая EULA, loopback bind, разные имена и UUID ровно двух клиентов и
loopback-адрес обеих фактических сетевых сессий. До двух подключений сцену он
не создаёт. Industry ledger должен быть пустым; занятая площадка отклоняется.

В отдельной арене около8192/180/8192 создаются настоящие Blueprint3 станция,
подстанция и завод, связанная сеть, сохранённый оплаченный заказ и энергия.
Игроки теста переводятся в Creative и наблюдают контроллер изнутри завода.
Состояние сохраняется в обычном IndustryData, без второго промышленного ledger.

Проверки выполняются с интервалом20тиков, чтобы Jade cache успевал истечь:

- Владелец получает ограниченный payload с текущим заказом/прогрессом.
- Чужой игрок не получает FrontierIndustry и универсальные JadeEnergyStorage/
  JadeEnergyStorageUid, а его запрос заказа не изменяет сохранённый ledger.
- Расстояние13блоков отклоняется, точная граница12блоков допускается.
- Spectator не получает промышленные сведения или generic FE.
- Те же координаты в другом измерении не открывают Overworld объект.
- Поддельный запрос к далёкому выгруженному чанку не создаёт ответа/загрузки.
- Разрушение критической подстанции и её восстановление отражаются в Jade и
  общей PDA state; оплаченный прогресс не изменяется во время остановки.

Запрос формируется точным Jade11.13.3 BlockAccessor.toNetwork и поступает в
BlockAccessorImpl.handleRequest. Поэтому работают штатные wire decode,
distance/chunk guards и полный зарегистрированный server-provider stack,
включая generic energy fallback и его приватный scrubber. Пробы генерирует
серверный test helper; это отдельно указано в отчёте, чтобы не выдавать их
за наблюдение полученных клиентом сетевых пакетов.

Результат — pis1-dedicated-checks.json. Поле serverChecksPassed относится к
серверным проверкам. Итоговый passed=true записывается только после завершения
lifecycle и всех подтверждений обоих клиентов; completedAt появляется в конце.
Историческое поле clientVisualEvidence содержит первоначальную строку pending;
итог доказан lifecycle.clientAcknowledgements, passed и acceptanceStatus. Helper
сам не останавливает сервер и не закрывает окна.

## Два клиента и доказательства

`tools/run_dedicated_observations.py <server-profile> <owner-profile> <foreign-profile>`
передаёт этапы в два независимых client observer. Он проверяет три свежих
manifest, runId и наличие отдельного test-only helper. Для этапов reconnect
действительно отключает и заново подключает чужой клиент, затем ждёт свежие
подтверждения обоих окон. Клиент сам выполняет ray trace, ждёт новый Jade
payload, сверяет worker/press flags и сохраняет PNG. Сервер не засчитывает
одни серверные wire-пробы за клиентское наблюдение.

V9 завершён 2026-10-25 в 12:10:55 UTC, runId
`18c2a27d-ac4c-48f1-8373-5abd66e7fe61`. [Итоговый отчёт](pis1-evidence/dedicated-checks-v9.json)
содержит 63 успешные проверки и 13 двухклиентных этапов:

1. Jade: питание, разрыв сети, восстановление — у владельца свежие разрешённые
   данные, у чужого нет промышленного или generic FE payload.
2. Ремонт: недоступный путь, работа, смерть и пауза, настоящая выгрузка/загрузка
   чанков, reconnect, одно завершение. Зафиксированы 3 попытки поиска пути,
   1800 общих рабочих тиков, один комплект и возврат прежнего UUID после загрузки.
3. Пресс: работа, остановка после разрыва сети, восстановление и reconnect.
   Оба клиента видят согласованные server flags; чужой клиент дважды сохраняет
   исходный UUID после фактического переподключения.

V8 обнаружил production bug: косметическая синхронизация пресса читала Level
API, создавая UNKNOWN chunk tickets и удерживая чанк после ухода игроков.
Минимальная правка использует getChunkNow и чтение из уже загруженного чанка.
Тот же сценарий V9 подтвердил настоящий unload и продолжение сохранённого ремонта.
Замеры MSPT V6 предшествуют этой правке и не заявляются точным замером JAR V9.

MC-Pilot 0.20.2 дополнительно подтвердил status/screenshot обоих клиентов через
CLI; [порядок работы](MC-PILOT-RU.md). Он установлен только в тестовые профили.
Чистый `run-pis1-final` содержит 33 мода без helper/MC-Pilot и миров.

## Книга и реальный Mavic

Walkthrough включается отдельно, только после успешного финального dedicated
отчёта. В серверном профиле создаётся pis1-drone-control.json с тем же runId и
action=start. Сервер публикует pis1-drone-stage.json; локальный bridge передаёт
его владельцу с точным clientRunId и возвращает pis1-drone-ack.json. Ровно два
разрешённых loopback-клиента должны оставаться подключёнными. Серверный setup
создаёт свежую площадку и явно выдаёт тестовые предметы; полёт выполняется
реальными client placement/interact/use и native SBW movement packets.

[Отчёт V9](pis1-evidence/dedicated-drone-walkthrough.json) завершён в 12:11:59 UTC:
26/26, 4 PNG controllers/flight при GUI Scale 2/3 и PNG настоящего полёта.
Один физический Mavic сместился на 34.8285 блока; получены 78 native packets и
78 наблюдений камеры у дрона. Выход сохраняет пару; исходный инвентарь восстановлен.
`testSupplies=true`, `purchaseProof=false`, `researchProof=false`: это OP/Creative
операторский сценарий. Проверка инструкции человеком-новичком отдельно не проводилась.

После V9 исправлено экранирование соседних динамических клавиш в Patchouli:
между ними добавлены пробелы вокруг `/`. Два новых игровых кадра при Scale 2/3
подтвердили вывод назначенных клавиш без сырых тегов;
[отдельный отчёт](pis1-evidence/guide-key-markup-recheck.json) сохраняет эту проверку.
Все 149 runtime `.class` финального JAR побайтно совпадают с V9; отличается ресурс книги.

После завершения сценариев, в 12:18:09 UTC, foreign-клиент упал при обычном
рендеринге: SIGSEGV в native `JNI.invokeD`, следующий Java frame —
Flywheel 1.0.5 `FrameUniforms.writeTime`. Нативный стек не удалось получить;
причина и связь с MC Pilot не установлены. [Сводка сбоя](pis1-evidence/post-acceptance-native-crash.json)
сохраняет время, стек и SHA локального hs_err без адресов сервера и личных путей.
Сценарные отчёты V9 завершены до этого сбоя; длительная стабильность клиента
остаётся неподтверждённой. Владелец после повторной проверки книги закрыт штатно,
сервер сохранил все измерения перед остановкой.

Для EULA-ожидания и любой неначатой проверки не ставить критерий Jira выполненным.
Успех javac или серверного provider-stack теста сам по себе не подтверждает
клиентский overlay, dedicated classloading или согласованное изображение.
